# Documentation chat

Dory can add an **Ask Dory** assistant to your site. It is optional. The browser sends questions to a same-origin `/api/chat` endpoint; only the server calls your model provider. Answers include links to the documentation sections used as sources. When the docs have no matching source, the assistant says it cannot find the answer.

## Configure a model

Set these environment variables on the server running `dory dev` or `dory preview`:

```bash
DORY_CHAT_API_KEY=your-server-only-key
DORY_CHAT_MODEL=gpt-6-luna
# Optional: an OpenAI-compatible provider endpoint; defaults to https://api.openai.com/v1
DORY_CHAT_BASE_URL=https://api.openai.com/v1
```

If your existing `.env` uses `OPENAI_API_KEY`, Dory accepts that as a fallback. Set `DORY_CHAT_MODEL` as well; no model is chosen silently.

The chosen provider must support the OpenAI-compatible `/chat/completions` API and `max_completion_tokens`. Keep the key in your server's secret manager or an uncommitted `.env` file. **Do not use a `VITE_` prefix** for the key: Vite exposes variables with that prefix to browser code. Dory never puts `DORY_CHAT_API_KEY` in the generated site or sends it to the browser.

Run `dory dev` while writing, or `dory build && dory preview` to serve the built site with chat. A static-file host cannot execute `/api/chat`; if you deploy `dist/` to one, put a compatible server endpoint behind the same path. Dory hides the chat button when no backend is configured.

When enabled, Ask Dory appears in the documentation search dialog. Readers can switch to chat, choose a suggested question, or select the Ask Dory result above page matches to ask their current search query. Supported answers include citations and documentation-focused follow-up questions. If a question is outside the published docs, Ask Dory says so without attaching an unrelated source and suggests topics from your configured questions instead.

To customize the suggested questions for your site, add this optional section to `dory.json`:

```json
"chat": {
  "suggestedQuestions": [
    "How do I install the product?",
    "What should I try first?",
    "Explain this page"
  ]
}
```

Without this section, Dory suggests questions based on your site name. Keep provider keys in the server environment, never in `dory.json`.

## Diagrams and media in answers

Ask Dory can explain documented workflows with Mermaid diagrams, formatted tables, and code examples with copy controls. Diagrams use your site's colors and fonts and adapt when readers switch themes.

Answers can also include images, video, and audio referenced in the cited documentation. Add media to your MDX using Markdown images or literal `src` attributes on `<img>`, `<Image>`, `<video>`, and `<audio>` elements. Local assets must exist inside your documentation directory; explicit HTTPS media URLs are also supported. Include descriptive alt text or a title so Dory can choose relevant media. The model selects verified asset IDs; it cannot invent media URLs. Video and audio use playback controls and never autoplay.

Media is included when relevant to the answer. Dory does not generate images or search the web for illustrations. A static host or reverse proxy must allow the media's origin in its content security policy.

## Serving-only containers

Build `pnpm run build:server` to produce `dist-server/server.js`, then run that bundle with Node from your site's directory. Supply `dist/`, `dory.json`, and the authored MDX files used for source retrieval. The Dory version is embedded in the bundle; a customer site does not need Dory's package.json or build toolchain at runtime. The default package build includes this serving bundle.

Keep model credentials in the runtime environment or a mounted secret. Do not copy local `.env` files into the image. The server can run as a non-root user with a read-only filesystem and a writable temporary directory.

## Limits and security

The backend rejects cross-origin requests, oversized messages, long conversation histories, and requests beyond its limits. The defaults are deliberately conservative:

When using `dory dev` on `localhost`, `127.0.0.1`, or `::1`, Dory skips the per-minute and daily request quotas so you can iterate on chat locally. The concurrent-call guard still applies. `dory preview` and deployed servers keep the quotas below.

| Environment variable | Default | Purpose |
| --- | ---: | --- |
| `DORY_CHAT_PER_MINUTE` | `3` | Requests per IP per minute |
| `DORY_CHAT_PER_IP_DAY` | `20` | Requests per IP per day |
| `DORY_CHAT_GLOBAL_DAY` | `100` | Requests across the server per day |
| `DORY_CHAT_MAX_CONCURRENT` | `2` | Simultaneous model calls across the server |
| `DORY_CHAT_MAX_OUTPUT_TOKENS` | `1000` | Maximum model output tokens (up to 2000) |

Malformed JSON and invalid questions are rejected before time quotas are charged. The concurrency guard still applies while request bodies are being read.

Each request has a 20-second provider timeout. A question can contain at most 600 characters, and at most six previous turns are accepted. The limits above apply **per Node process**; for multiple replicas, enforce shared limits at your reverse proxy or edge as well. Dory uses the connection IP by default and ignores untrusted `X-Forwarded-For` headers. If you put the server behind a reverse proxy, configure limits there using its verified client IP.

When running behind trusted reverse proxies, set `DORY_CHAT_TRUSTED_PROXY_CIDRS` to their source CIDRs and `DORY_CHAT_PROXY_HOPS` to the number of addresses they append to `X-Forwarded-For`. Only requests received from those peers use the configured address counted from the right; client-supplied prefixes and headers from untrusted peers cannot change the quota identity. For Google's external Application Load Balancer, the appended pair is client IP then forwarding-rule IP, so use `2` hops. Never trust arbitrary proxy source ranges. See [Google's header semantics](https://docs.cloud.google.com/load-balancing/docs/https#x-forwarded-for_header).

The server retrieves relevant MDX sections and gives only those excerpts to the model. It validates returned source IDs before showing an answer. Model output can still be imperfect, so keep examples and API facts reviewed and use `dory check` in CI.
